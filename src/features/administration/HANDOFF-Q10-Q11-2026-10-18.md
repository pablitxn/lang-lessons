## P2/root wiring requests

- `AdminUsers` adds `managementApi`, `managementCapabilities`, `onAccountChanged`.
  Existing `capability` still gates the entire admin list. Each action separately
  needs an explicit granted capability; no role mapping is embedded in the UI.
- `ManagedUser` adds `disabled` to frozen `PublicUser` for this view adapter.
  Existing minimal public users remain renderable but have no mutation controls.
  No email/name/authentication record is added to read disclosures.
- `UserManagementApi.apply(change, signal)` accepts feature-local `UserChange`:
  create with email + explicitly selected role; change-role with user ID + role;
  set-disabled with user ID + boolean. This is an adapter proposal, not an edit to
  shared contracts or a claim that the P2 HTTP API already exists. Root maps it to
  P2 and supplies no browser-selected actor. Creation collects no password,
  temporary credential or recovery configuration. If handoff policy prevents
  creation, return `policy-unresolved`; do not fabricate credentials or claim
  activation. No live provisioning was performed.
- Adapter results: `applied`, `denied`, `last-administrator`, `conflict`,
  `invalid-input`, `policy-unresolved`. Server must enforce current actor role,
  CSRF, input validation, transaction safety and last ACTIVE administrator
  protection across concurrent requests. UI never counts a page of admins to
  infer safety. No optimistic role/active-state success is shown.
- Native modal confirmation supports cancel/Escape/focus. A pending request
  cannot be canceled or double-dispatched. Successful mutations reload the
  visible list; root must refresh current actor/capabilities via
  `onAccountChanged`, especially for self changes. Denial clears the list and
  controls. Conflict requests a list refresh. A thrown transport failure has an
  ambiguous outcome: controls lock, no retry or duplicate creation is dispatched,
  and reconciliation is required. Root must not automatically remount/retry an
  ambiguous mutation as a recovery policy.
- P2 branch was inspected at `44bd503185245e4e2f53169a818d0817f513b7be`:
  it supplied only read APIs at inspection time. Actual mutation adapter mapping
  and isolated DB/last-admin safety evidence remain P2/integrator work. No server
  imports were added to the browser modules.
- `StudentProgressView.daily` optionally supplies `{ timeZone, days }` where each
  day has a server-selected ID/label, nullable written totals, and its session
  records. Root must supply whole-day totals across visits from underlying
  attempts/results, not sum only a displayed session page. Numeric projection
  fields are performed/solved/mistakes plus `definitionVersion`; set written to
  null until those definitions are accepted. Their availability is NOT inferred
  from this Q11 grouping answer. Zero is displayed only when explicitly supplied.
- `StudentSessionView` adds optional `startedAt`/`endedAt` display strings. No
  browser Date conversion, timezone default, active-time calculation, session
  aggregation or call-derived written total exists. Daily grouping is omitted/null
  until a boundary is selected; the UI explicitly reports unavailable grouping
  and retains existing session displays. Parent/P2 owns pagination and complete
  projection transport. These are feature display interfaces, not persistence DTOs.
