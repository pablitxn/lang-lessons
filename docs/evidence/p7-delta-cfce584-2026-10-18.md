## F5 — P2: pending events are not durably written while an earlier network send is stalled

Exact locations:

- `src/features/progress/queued-progress-sink.ts:41-44`, `:53-55`, `:70`, `:92-97`.
- Same independently reachable behavior in `src/features/progress/written-usage-queue.ts:18`, `:21-24`, `:31`, `:47-48`.

Both queues put new work into a JavaScript array, then serialize its entire persistence-and-network drain behind the existing request. If the first send has not returned, later submissions do not reach IndexedDB. The status correctly reports unsaved work, but a tab reload/crash loses it; the approved pending-queue durability is not implemented for this ordinary slow-network window. This is separate from missing root recovery composition: the entries are absent from storage and cannot be recovered even by a perfect resume flow.

Minimal reproduction, independently run in actual Chromium/IndexedDB against these unmodified modules:

1. Create both queues with real IndexedDB stores and transports returning unresolved promises.
2. Submit progress e1 and usage `visible`; wait until both transports are entered. Their rows are durable.
3. Submit progress e2 and usage `input`; allow asynchronous local work to settle.
4. Inspect IndexedDB: only e1 and visible exist; each queue reports unsaved=1.
5. Reload the page and reopen both stores: e2 and input are absent.

Actual observed output:

```json
{"before":{"persisted":["e1"],"usage":["visible"],"unsaved":1,"usageUnsaved":1},"after":{"persisted":["e1"],"usage":["visible"]}}
```

Test: `tests/integration/p7-durability-browser.test.ts`. Its passing assertion deliberately reproduces the defect, not durability acceptance. Fix by allowing local append transactions to progress independently of the serialized remote drain, preserving event/sequence ordering, scope checks, acknowledgment fencing, and flush waiting for all local and remote work. Add a stalled-send/reload regression for both queue types.
