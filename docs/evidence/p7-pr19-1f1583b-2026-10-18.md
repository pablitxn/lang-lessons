## F6 — P2: cancelling while broker reservation is pending still dispatches provider creation

Location: `server/realtime.ts:168-176`, specifically the awaited `authority.reserve` at line 174 and unconditional provider fetch at line 176.

The disconnect guard runs before database reservation. While reservation waits, the browser can cancel and the server response close handler sets `disconnected=true`. After reservation returns, the server does not recheck that flag; it installs the lease and dispatches a new provider call for a client already known to have left. The later successful-response path hangs it up, but that cannot undo avoidable call creation/cost. An upstream timeout can also leave the reserved receipt unresolved.

Independent minimal reproduction uses the real `createRealtimeServer`, a deliberately held authority reservation, a loopback HTTP client and a fake provider (no external requests):

1. POST a valid SDP and canonical segment; hold `authority.reserve()` before resolution.
2. Abort the client request and wait until the server response emits `close`.
3. Verify zero provider creation calls so far.
4. Release reservation. Observe one provider creation call despite the known cancellation.

`tests/integration/p7-pr19-races.test.ts` reproduces this. Its passing assertion describes the defect, not acceptance. Recheck cancellation after asynchronous reservation and before dispatch; reconcile the durable reservation as definitively not dispatched. Preserve the existing cleanup of calls whose dispatch actually occurred before cancellation. Add a regression expecting zero provider calls in this window.
